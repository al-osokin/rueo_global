# Parser v4 RFC (черновик)

## Зачем
Текущий парсер сочетает:
- детерминированный разбор структуры,
- эвристики семантики,
- постобработку для review UI.

Из-за этого локальные фиксы регулярно вызывают регрессии в уже просмотренных статьях.

Цель v4: разделить уровни ответственности и сделать ядро устойчивым к регрессиям.

---

## Принципы
1. **Сначала структура, потом смысл**.
2. **Минимум эвристик в ядре** (никаких «угадать перевод» в structural pass).
3. **Явный JSON-контракт** между этапами.
4. **LLM только поверх структурных блоков**, а не по сырому тексту статьи целиком.
5. **Обязательная регрессия на golden-наборе** после любого изменения.

---

## Scope v4 (этап 1: deterministic core)

### 1) Сегментация статьи
- выделение заголовка статьи (`[abort|i]`),
- выделение вложенных словоформ (`[~a]`, `[~ig/o]`),
- сохранение иерархии по отступам,
- сохранение порядка блоков без перестановок.

### 2) Нормализация строк
- склейка логических продолжений по отступам,
- перенос «перетёкшего» курсива между строками,
- сохранение разделителей (`;`, `,`, `:`) как токенов,
- запрет на слияние, если это ломает границы numbered-блоков.

### 3) Numbered-блоки
- выделение значений `1.`, `2.`, ... внутри словоформы,
- привязка примечаний к значению или словоформе по уровню отступа,
- сохранение исходного порядка.

### 4) Tilde expansion
- раннее раскрытие тильд в словоформах:
  - `[abort|i]` + `[~a]` -> `aborta`,
  - `[~ig/o]` -> `abortigo`.
- хранить и сырой, и раскрытый вид.

### 5) Базовые типы блоков (без deep-semantic)
- `headword`
- `subheadword`
- `sense` (optional `number`)
- `note`
- `reference`
- `example_raw` (пара ещё не подтверждена)
- `text_raw`

> На этом этапе v4 **не обязан** идеально решать «перевод/пример». Он обязан стабильно и полно вынести структуру.

---

## Этап 2: semantic layer (LLM/Gemma)
На вход подаётся уже сегментированный блок (а не вся статья):
- `sense`/`example_raw`/`note` в пределах одной словоформы.

На выходе (строго по схеме):
- `translation_items[]`
- `examples[]` с парой `eo`/`ru`
- `labels[]` (`мед.`, `перен.` и т.п.)
- `references[]`
- `confidence` + `needs_human_review`.

---

## JSON-контракт (минимальный, v4)

```json
{
  "article": {
    "headword": { "raw": "[abort|i]", "expanded": "aborti" },
    "forms": [
      {
        "raw": "[~a]",
        "expanded": "aborta",
        "blocks": [
          { "type": "sense", "number": null, "tokens": [] },
          { "type": "note", "scope": "form", "tokens": [] },
          { "type": "example_raw", "tokens": [] },
          { "type": "reference", "mode": "see|compare|link", "targets": [] }
        ]
      }
    ]
  }
}
```

## Совместимость с текущим UI
- текущий `/admin/review` временно питается legacy-слоем;
- v4 добавляет адаптер `v4_ast -> review_payload`;
- переключение через feature flag (`PARSER_ENGINE=legacy|v4|hybrid`).

---

## Golden regression set (первый пакет)
Минимум:
- `1` (буква, курсивные пояснения),
- `2` (ранние формы + сокращения),
- `3` (толкование + примеры `beta бета`),
- `6` (аналогично с несколькими примерами),
- `56` (сложный перенос курсивной скобки + `_ср._`),
- `77` (numbered + переносы + сокращения).

Для каждого кейса хранить:
- input (`priskribo`),
- expected structural AST,
- expected review projection (минимально важные поля).

---

## План миграции
1. Зафиксировать текущий JSON-контракт legacy (snapshot).
2. Реализовать v4 structural pass без semantic догадок.
3. Добавить snapshot-тесты golden-набора.
4. Подключить LLM semantic layer в режиме `hybrid`.
5. Сравнить `legacy vs hybrid` на первых 200 статьях.
6. Включить v4/hybrid для review-потока, оставив fallback на legacy.

---

## Вне scope (пока)
- Полная автообработка ru->eo с «восстановлением структуры интуитивно».
- Автопринятие low-confidence решений без оператора.
- Массовый crowdsourcing и уровни компетентности (это отдельный RFC).

---

## Критерии успеха
- После фикса в v4 не растёт число регрессий в golden-наборе.
- Кнопка reparse стабильна (без 500).
- В id `3/6/56/77` не теряются примеры, numbered и ссылки.
- Для поиска доступны раскрытые формы (`~` -> full) и пары `example eo/ru`.

## UI для верификации parser-v4 + Gemma-4 (draft requirements)

Цель: заменить просмотр сырого JSON интерфейсом структурной проверки и обучения.

### Основные режимы
1. **AST Review**
   - дерево: `form -> sense -> note/reference/example`
   - рядом исходные строки (`raw_lines`) и результат разбора
   - подсветка подозрительных мест (merge/range/reference leakage)

2. **Gemma Assist (interactive)**
   - на выбранный блок отправляется структурный контекст (не вся статья)
   - Gemma предлагает один или несколько вариантов нормализации
   - оператор выбирает вариант или даёт ручную правку
   - выбор сохраняется как `resolution` + training signal

3. **Diff/Regression View**
   - сравнение `legacy/v3` vs `v4` vs `v4+gemma`
   - быстрые чекпоинты по golden-набору (1,2,3,6,56,77)

### Что нужно хранить в данных для UI
- `sense_number`
- `note_scope`: `form|sense`
- `example_eo`, `example_ru`
- `source_span`/`raw_fragment` для трассируемости
- `confidence`/`needs_human_review` для gemma-результатов
- `operator_action` (accept/edit/reject)

### MVP интеграции Gemma-4
- endpoint `POST /admin/v4/resolve-block`
  - input: `article_id`, `form_id`, `block_id`, `context`
  - output: `candidates[]`, `confidence`, `rationale_short`
- endpoint `POST /admin/v4/apply-resolution`
  - сохраняет операторское решение и помечает блок как resolved
